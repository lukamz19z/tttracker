# V1 Ladder Register: manual numbers and replacements

The later serial-number, height-measurement and filtered Print PDF extension is documented in [V1 ladder serial, height and print](v1-ladder-serial-height-print.md).

1. **Source of the generated number:** `getNextLadderNumber()` in `app/(protected)/assets/equipment/ladders/page.tsx` scanned loaded `LAD-<digits>` values, incremented the maximum and fell back to `LAD-001` for an empty list. The Add form displayed that generated value in a disabled Asset ID input and inserted it as `ladder_number`. There was no literal `LAD-001` production constant to remove. The connected V1 project currently has no `equipment_ladders` table, so failed loads also left that list empty. All remote inspection for this task was read-only; V2 was not inspected or changed.
2. **Files changed:** see the list below. Changes remain within V1 ladders, their existing shared document/detail integration, migration, verification and documentation.
3. **Manual number:** Add Ladder starts empty and requires Ladder Register Number near the top, with `e.g. LAD-001-R1` and the requested physical-register helper. Surrounding whitespace is trimmed; display case and valid suffixes/custom identifiers are preserved. No generation or optional auto-increment remains. Existing identifiers remain locked when editing, matching the previous UI's intentional disabled identifier field. All existing make/type/height/crew/inspection/status/notes fields remain.
4. **Duplicate validation:** immediate form feedback plus database enforcement on `upper(btrim(ladder_number))` for all non-superseded ladders. Active, Out of Service, Missing and Retired numbers remain reserved; Superseded history may share an explicitly reused number. Controlled API errors say `A ladder with register number <number> already exists.` Concurrent saves are protected by the unique index, not just a browser check. No duplicate-key details reach the user.
5. **Replacement relationship:** the new ladder stores `supersedes_ladder_id` referencing the old ladder's UUID. A unique index gives each old ladder at most one direct replacement. The reverse `Superseded by` relationship is derived by UUID, avoiding two independently mutable links. Both relationships display clickable saved numbers in the register, editing details and equipment/document detail page. A new ladder-specific detail endpoint supplies the existing detail UI's previously missing API.
6. **Superseded status:** the new form offers searchable existing ladder selection. Selection shows the proposed lifecycle change, and Save requires confirmation stating `<old> will be marked as Superseded by <new>.` The database requires that explicit confirmation flag, locks the old record, creates the Active replacement and marks the old record Superseded in one transaction. Failed creation rolls everything back. Superseded timestamp and acting user UUID are recorded. Linked replacements cannot be deleted, relinked or reactivated. Existing status filters now include Active, Superseded and All alongside the other current statuses; the original all-record default remains.
7. **History preservation:** no existing numbers are rewritten. The old/new UUIDs, inspection dates, notes, equipment document rows and SharePoint references remain independent. Replacement creation does not copy, move, overwrite or delete the previous ladder's documents or inspections. A replacement can itself later be superseded, preserving the chain.
8. **Search and generated references:** existing partial, case-insensitive register search continues to use `ladder_number`. CSV uses the actual saved number and now includes Supersedes/Superseded By columns. Existing `equipmentLabel` and SharePoint folder synchronization use the actual saved ladder number. Document uploads preserve sanitized original filenames inside that ladder's saved-number folder; no hard-coded ladder number was found. No V1 ladder-specific PDF, QR, barcode or label generator was found. Ladder document upload/read now uses the same existing dynamic Assets permissions as the ladder APIs; other equipment retains its existing authorization behaviour.
9. **Migration:** `supabase/migrations/20261029120000_v1_ladder_manual_numbers_and_replacements.sql`. Required for stable replacement links, audit fields, unique comparison and the transactional save function. It also creates the code-referenced V1 ladder table only if absent, using the fields already consumed by the current page. Existing tables/rows are retained. If an existing installation contains conflicting current numbers, the migration aborts with an explicit reconciliation message; it never auto-renames/deletes data. No prior migration was edited. Not applied remotely.
10. **Website deployment:** required, with V1 client/API changes and the new migration deployed together. Not deployed by this task. Uses existing configurable `tt.assets`, `tt.assets.equipment`, `assets.view` and `assets.edit` permissions, with no new role-name checks or permission grants. Authenticated direct reads have matching RLS; writes go through the authenticated server and transactional RPC.
11. **Mobile OTA / native rebuild:** neither is required. No mobile, native or V2 files changed.
12. **Validation:** `npx tsc --noEmit`, `npm run build`, changed-file ESLint and `node scripts/verify-v1-ladders.mjs` pass. Tests execute the migration twice against local PostgreSQL for both existing-table and missing-table installations; exercise the real save/API functions, case-insensitive duplicate errors, replacement confirmation, transaction rollback, immutable existing numbers/links, history preservation, permission denial, detail relationships and rendered stable-ID links. They also confirm conflicting legacy identifiers are preserved when migration is rejected. Browser smoke testing and simultaneous-session testing against a migrated staging database remain rollout checks; no production writes were used for testing.
