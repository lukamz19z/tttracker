# V1 Ladder Register: serial, height measurement and Print PDF

1. **Files changed:** `lib/assets/ladders.ts`; `app/api/assets/equipment/ladder/route.ts`; `app/(protected)/assets/equipment/ladders/page.tsx`; `components/assets/equipment-document-detail.tsx`; new `components/assets/ladder-print-register.tsx`; `scripts/verify-v1-ladders.mjs`; the new migration below; and this report. The previous ladder report links here. No V2 or mobile code changed.
2. **New migration:** `supabase/migrations/20261029130000_v1_ladder_serial_height_measurement.sql`. Adds nullable `serial_number text` and `height_measurement_type text` without database defaults or backfills. Replaces the existing save RPC body to persist the fields while retaining its signature, permissions, identifier protection and atomic replacement checks. The applied `20261029120000_v1_ladder_manual_numbers_and_replacements.sql` remains unchanged. Remote schema/function inspection was read-only; the new migration was not remotely applied.
3. **Serial Number:** optional, independent manufacturer/supplier identifier, editable and non-unique. The manual internal ladder register number remains canonical and required. Serial appears beneath the number in compact rows/cards, in details, in search, CSV and a separate print column. Missing serials display an em dash in the register/detail/print views.
4. **Height Measurement:** per-ladder editable basis, with Platform Height, Overall Height, Working Height and Other suggestions. The user may also enter a custom basis, without a code/configuration deployment. It is not a fixed enum. The actual height remains compatible text, including units, with no numeric schema conversion.
5. **New-ladder defaults:** the website form defaults the basis to Platform Height; the user can change it. No database default forces that value onto other clients or historical records. The height helper asks for explicit units, e.g. `1.8 m`.
6. **Historical behaviour:** existing heights are not rewritten; missing basis displays Not specified and opens blank during editing. Missing serial stays blank in the editor. Existing custom/unspecified ladder types are preserved during editing. Older API/RPC clients omitting either new key do not erase an existing value; an explicit blank/null clears it. Existing clients can create rows with both fields absent/null. Pure numeric historical heights display `(unit not specified)` rather than silently assuming metres; text such as `1.8m` is displayed as `1.8 m` without altering its stored value.
7. **Search:** serial and measurement basis join the existing partial, case-insensitive register-number, make, type, height, crew, status, note and inspection search. A shared filter function supplies the screen, CSV and print data.
8. **CSV:** respects the current filters and contains Ladder Register Number, Serial Number, Make, Ladder Type, Height, Height Measurement, Crew, Status, Last Internal Inspection, Inspection Status, Supersedes, Superseded By and Notes. Heights retain stored text/units; historical basis uses Not specified. Quoting and formula-leading cell protection are included.
9. **Print PDF:** the register's Print PDF button calls `printFilteredRegister()` and `window.print()`. The browser's Save as PDF output uses a separate hidden print register bound directly to `filteredItems`, with TTTracker / Ladder Register header, generated date/time, current filters and total rows. Columns include separate serial and measurement fields, crew/status/inspection information and replacement references; long notes and action buttons are excluded. The generation timestamp refreshes on `beforeprint`, including browser-native print commands.
10. **Lifting Gear logic reused:** its current `printFilteredRegister` browser-print action, hidden `print-area`, separate filtered table, count/time/filter header, visibility isolation, fixed full-width collapsed table, bordered compact cells and landscape page with 8 mm margins. Ladder-specific widths fit the extra metadata; repeated table headings, row break protection, and explicit removal of screen content/navigation are included. Lifting Gear itself was not modified and no separate PDF library/system was introduced.
11. **Superseded behaviour:** manual numbers, duplicate comparison, immutable identifiers, explicit confirmation, stable UUID relationships, old Superseded/new Active transaction, linked deletion/reactivation protection and separate history remain. Active print excludes Superseded rows; All includes them with their status. Replacement references may name a related ladder outside the filters without adding that ladder as a printed row.
12. **SharePoint:** unchanged canonical register-number identity. Folder/document helpers continue loading the saved ladder UUID/number. Serial does not become a folder identifier. Existing inspections, documents, UUIDs and SharePoint references are not moved, overwritten or deleted. The shared detail component displays new metadata only for ladder records; other equipment details retain their behaviour.
13. **Website deployment:** required for V1 client/API together, after or alongside the new migration. Not deployed by this task.
14. **Migration:** required and not applied remotely. No permission changes, serial uniqueness constraint, new mandatory column, default assignment, historical backfill or destructive unit conversion is included.
15. **Mobile OTA:** not required. Audited `mobile/app/(drawer)/assets.tsx`, which selects the existing table with `*` and writes the original fields, plus website equipment/compliance summaries and SharePoint sync consumers. Added nullable fields do not invalidate their old object shapes or require new input. The migration's save RPC also preserves omitted metadata. No mobile files were modified.
16. **Native rebuild:** not required; no native changes.
17. **TypeScript:** `npx tsc --noEmit` passes.
18. **Build:** `npm run build` passes for V1.
19. **Lint/tests/print QA:** changed-file ESLint and `node scripts/verify-v1-ladders.mjs` pass. Local PostgreSQL tests cover applying both migrations twice, untouched historical heights/null metadata, serial/basis create/edit/clear, duplicate serials, custom/Overall basis retention, older-client preservation, validation, and all previous replacement/permission/history safeguards. Actual shared filtering/CSV and rendered print tests verify the standard LAD-004/SN458392 case, Active/crew/type scopes, historical Not specified/serial dash, and All/Superseded rows. Headless Chrome printed the real print component/CSS using synthetic filtered, All and 85-row fixtures. PDF checks confirm landscape output, hidden navigation/controls, all expected rows, repeated headings on five pages and no blank pages. First/last-page rendered images were visually inspected; column widths were adjusted to avoid splitting the Last Inspection heading. This is local fixture/print QA, not a production write or a full authenticated post-migration browser session.

## Reproduce print QA

Set `TTTRACKER_LADDER_PRINT_QA_DIR` to a temporary directory before running the verification script to emit `active.html`, `all.html` and `multipage.html` from the real React print component. Open a fixture and print it, or use headless Chromium with `--print-to-pdf` and `--no-pdf-header-footer`. These are synthetic test records; no production data is included. Generated fixtures and QA PDFs belong outside the repository and are not deployed.
